# 升级计划：vite-plugin-vue2 适配 Vite 8

---

## 0. 核心原则

**不重写，只修补。** 当前代码架构合理，模块分工清晰。Vite 8 的插件 API 保持向后兼容（Rolldown 支持相同的 Rollup 插件接口），大部分代码只需适配性修改。

---

## 1. 环境与依赖

### 1.1 `package.json` 修改

```jsonc
{
  "name": "@vitejs/plugin-vue2",
  "version": "2.4.0",
  "peerDependencies": {
    "vite": "^8.0.0",
    "vue": "^2.7.0"
  },
  "dependencies": {
    // 无新增依赖。不要加 vue-template-compiler、vue-hot-reload-api、@rolldown/pluginutils
  },
```

- 不加 `@rolldown/pluginutils`：优先从 `vite` 导入 `createFilter`，仅在 Vite 8 移除时才替换

### 2.1 `src/index.ts` — 插件入口

**改动点：**

| 位置 | 当前 | 改为 | 原因 |
|------|------|------|------|
| L2 | `import { createFilter } from 'vite'` | 先确认 Vite 8 是否仍导出；若已移除则改为 `import { createFilter } from '@rolldown/pluginutils'` | Vite 8 可能不再转发此工具 |
| L85 | `name: 'vite:vue2'` | 不变 | — |
| L87-92 | `handleHotUpdate` | 不变 | 钩子签名兼容 |
| L94-109 | `configResolved` | 不变，但删除 L103-108 的 Vue alias 逻辑（见下方说明） | — |
| L111-113 | `configureServer` | **必须保留** | HMR 和 asset URL 依赖 `devServer` 引用 |
| L115-117 | `buildStart` | 不变 | — |
| L130-164 | `load` | 不变 | — |
| L166-219 | `transform` | 不变，`opt?.ssr` 可能需要适配（见 2.6） | — |

**关于 Vue alias 逻辑（[L103-108](src/index.ts#L103-L108)）：**

当前代码在 `configResolved` 中注入 `vue → vue/dist/vue.runtime.esm.js` 别名。Vite 8 中 `config.resolve.alias` 的数据结构可能变化（从数组变为对象或其他），需要验证。建议改用更安全的注入方式：

```ts
configResolved(config) {
  // ...existing logic...
  if (!config.resolve.alias.find((a: any) => a.find === 'vue' || a.custom?.find === 'vue')) {
    config.resolve.alias.push({ find: 'vue', replacement: 'vue/dist/vue.runtime.esm.js' })
  }
}
```

### 2.2 `src/main.ts` — 主模块代码生成 ⚠️ 核心改动

这是**最关键的文件**，因为使用了 `transformWithEsbuild`。

**改动点：替换 TS 转换方案**

当前逻辑（[L143-L161](src/main.ts#L143-L161)）：

```ts
// 当 SFC script 为 TypeScript 时，用 esbuild 转译
if (descriptor.script?.lang === 'ts' || descriptor.scriptSetup?.lang === 'ts') {
  const { code, map } = await transformWithEsbuild(resolvedCode, filename, {
    loader: 'ts', target: 'esnext', sourcemap: options.sourceMap
  }, resolvedMap)
}
```

**替换方案**（按优先级排列）：

**方案 A：使用 `transformWithOxc`**（推荐）
```ts
import { transformWithOxc } from 'vite'  // Vite 8 新增

if (descriptor.script?.lang === 'ts' || descriptor.scriptSetup?.lang === 'ts') {
  const { code, map } = await transformWithOxc(resolvedCode, filename, {
    lang: 'ts', target: 'esnext', sourcemap: options.sourceMap
  })
  resolvedCode = code
  resolvedMap = resolvedMap ? (map as any) : resolvedMap
}
```

**方案 B：移除此段转译，让 Rolldown 自行处理**
```ts
// 删除整个 if 块
// Rolldown/Oxc 原生支持 TS，transform 钩子返回的 TS 代码
// 可通过 meta.vite.lang 声明语言类型，让后续管线处理
```
这更简洁，但需要验证 Rolldown 是否会正确处理 `transform` 钩子返回的含 TS 语法的代码。如果 Vite 8 的 transform 管线支持 `meta.vite.lang` 声明后自动转译，这是最优解。

**其余部分不变：** `genScriptCode`、`genTemplateCode`、`genStyleCode`、`genCustomBlockCode`、`linkSrcToDescriptor`、`attrsToQuery` 均无需改动。

### 2.3 `src/compiler.ts` — 编译器解析

**不需要改动。** 当前实现已正确处理 Vue 2.7 的 `vue/compiler-sfc`：

```ts
// 当前代码已经正确 —— 通过 createRequire 从项目根解析 vue/compiler-sfc
const compiler = tryRequire('vue/compiler-sfc', root) || tryRequire('vue/compiler-sfc')
```

Vue 2.7 的 `compiler-sfc` API（`parse`、`compileTemplate`、`compileStyleAsync`、`compileScript`、`rewriteDefault`）与 Vue 3 对齐，当前代码使用的就是这些 API，无需任何封装。

### 2.4 `src/utils/descriptorCache.ts` — 描述符缓存

**不需要改动。** 包含完整的缓存逻辑（`prevCache`、`src` 导入、自动文件读取、hash ID 计算），计划中简化为单一 `Map` 会导致功能崩溃。

### 2.5 `src/script.ts` — 脚本编译

**不需要改动。** 使用 `WeakMap` 缓存、`compiler.compileScript`，均为稳定 API。

### 2.6 `src/template.ts` — 模板编译

**改动点：验证 `devServer` 相关逻辑**

[L108-L119](src/template.ts#L108-L119) 在开发模式下通过 `options.devServer.config` 获取 base URL 和 origin。Vite 8 中 `devServer.config` 结构可能变化，需要验证 `server.origin` 和 `config.base` 的路径是否仍然兼容。

**改动点：确认 `hash-sum` 和 `slash` 依赖**

这两个是 `devDependencies` 中的包，代码中有使用。确保 Vite 8 环境下版本兼容。

### 2.7 `src/style.ts` — 样式转换

**改动点：验证 `formatPostcssSourceMap`**

[L4](src/style.ts#L4) 从 `vite` 导入 `formatPostcssSourceMap`。此函数在 Vite 3 时就曾改为异步，Vite 8 中可能进一步变更或移除。

**验证策略：**
```ts
// 如果 Vite 8 仍导出，确认签名是否变化
import { formatPostcssSourceMap } from 'vite'
// 如果返回类型从 Promise<RawSourceMap> 变为 RawSourceMap，去掉 await
const map = result.map ? await formatPostcssSourceMap(result.map as any, filename) : ...
```

如果已移除，则自行实现简易版：
```ts
function formatPostcssSourceMap(map: any, filename: string) {
  if (!map) return { mappings: '' }
  map.file = filename
  return map
}
```

### 2.8 `src/handleHotUpdate.ts` — HMR 更新检测

**不需要改动。** 使用的是标准 Vite `HmrContext` 和 `ModuleNode` API，Vite 8 保持兼容。

### 2.9 `src/utils/hmrRuntime.ts` — HMR 运行时

**不需要改动。** 自包含的运行时代码，不依赖任何 Vite 内部 API。

### 2.10 `src/utils/componentNormalizer.ts` — 组件归一化

**不需要改动。** 纯运行时代码，与构建工具无关。

### 2.11 `src/utils/query.ts` — 查询参数解析

**不需要改动。** 纯字符串解析，不依赖 Vite API。

### 2.12 `src/utils/error.ts` — 错误处理

需要确认 `PluginContext.error()` 的错误格式在 Vite 8 中是否兼容。

## 6. 风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| `transformWithOxc` API 不稳定 | 中 | 高 | 先用方案 B（让 Rolldown 自行处理 TS），或在 `devDependencies` 中保留 `esbuild` 仅用于此场景 |
| `formatPostcssSourceMap` 被移除 | 中 | 低 | 自行实现简易版（5 行代码） |
| `createFilter` 从 `vite` 移除 | 低 | 低 | 从 `@rolldown/pluginutils` 导入 |
| Rolldown CJS 互操作差异 | 中 | 中 | Vue 2.7 的 compiler-sfc 是 CJS，Rolldown 可能处理方式不同，需实测；如有问题用 `legacy: { inconsistentCjsInterop: true }` |
| `devServer.config.server.origin` 变更 | 低 | 低 | 打印值确认，调整路径拼接 |

---

**总结：实际需要改动的只有 3 个文件**——[main.ts](src/main.ts)（替换 esbuild）、[style.ts](src/style.ts)（验证 formatPostcssSourceMap）、[index.ts](src/index.ts)（验证 createFilter 和 alias）。其余 9 个文件无需变动。先跑通 L1 冒烟测试，再逐层推进。

建议下一步先看 [脚本编译与缓存](6-script-compilation-and-caching) 和 [模板编译策略](7-template-compilation-strategy)，理解 `transformWithEsbuild` 的上下文再动手替换。
